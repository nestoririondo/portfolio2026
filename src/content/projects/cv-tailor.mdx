Before CV Tailor there was a Google spreadsheet and a lot of copy-pasting. The spreadsheet recorded where I had applied, when, and what came back. The CV itself lived in Canva, in a design I liked. For each application I pasted the job requirements into Claude, pasted the text of my CV after them, and asked for the CV to be tailored to the ad: use its keywords, reorder by relevance, invent nothing. Then I copied the result back into Canva.

Three things were wrong with that. There was a lot of manual copying. Pasting the new text into Canva broke the layout every time. And nothing connected the tailored CV to the row in the spreadsheet.

The app began as a replacement for the spreadsheet and grew to cover the rest. What it kept from the manual version is the division of work: the AI writes a draft from my facts, and I read it, correct it and send it. This page describes how that division is built into the product, along with the limits on what the AI sees and what it may cost. For what the product does today, the [landing page](https://usecvtailor.com/?ref=portfolio) is the better place.

## The AI drafts, a person decides

Tailoring a CV creates a draft application and nothing more. Sending is a separate step that only the person takes.

- **Drafts stay drafts.** A tailored CV is saved with the status "draft". It reaches an employer only when you download it or send it yourself.
- **Emails are drafted, not sent.** The AI writes the application email, and the dialog shows it with a "Written by AI" badge that changes to "Edited" once you alter the text. You choose whether to send it through the app or from your own mail program. Follow-up emails work the same way.
- **Every AI change can be undone.** Each revision by the chat stores the version from before it, for the CV and for the profile.
- **Your edit wins.** A revision takes a few seconds. If you change the CV by hand in that time, the AI's version is discarded and yours is kept.
- **Sent means frozen.** Marking an application as sent freezes its copy of the CV, so the record shows what went out.

## The AI works from stated facts

You enter your facts once, in a profile. Each tailored CV is a selection and rewording of those facts. The prompt names them as the only source of claims and forbids inventing skills, employers, dates, metrics or levels. A requirement the profile does not cover is listed as a gap beside the CV and is not written into it.

The job posting is treated as source data and not as instructions. The prompt tells the model to ignore any request hidden in a posting to change its rules or to fabricate something.

The profile assistant follows the same rule. When it rewrites duties as achievements and has no figure, it leaves the number out and asks for it. A made-up metric in the profile would spread into every CV built from it.

A prompt cannot prove that a CV is accurate, and nothing in the code can check a claim against reality. That is the reason the review step exists.

## Scores are counted in code

The model never writes a number. A percentage it made up would look precise without being checkable.

It does two smaller jobs. It classifies six to ten of the posting's requirements as met, partly met or missing, judged against the profile. And it lists the key terms a recruiter would look for in the posting. The code does the counting, and both lists are shown behind the scores, so every point can be traced to a requirement or a term.

Requirements are judged against the facts and not against the CV, so tailoring cannot inflate that score. Next to each tailored CV, short notes say what was moved, condensed or reworded, and why.

## What the model sees

- **Tailoring and matching** send the headline, the summary and the structured facts. Name, contact details and photo stay on the server and are added when the CV is rendered.
- **Importing a CV** sends the whole document, including the contact details in it. There is no other way to read it.
- **The profile assistant** sees the name and contact fields, because it can edit them. It cannot reach the photo or the original import.
- **The email draft** includes your name, so the message can be signed.
- **The original import is not sent again.** A review found that the raw text of the imported CV still went along with every tailoring request, so a fact deleted from the profile could come back through it. That text is now excluded.

## Privacy in the structure

- **One database per person.** Each account has its own SQLite file. With one shared table, a single query that forgets its ownership filter can show someone another person's CV. Deleting an account deletes its folder.
- **Usage statistics without cookies.** Events are sent from the server, with a pseudonymous ID and fixed event names. They never contain CV text, email addresses or page paths.
- **Error reports without content.** Before an error report leaves the server, its message and stack trace are replaced by a category. The original stays in a log on the server for 14 days.
- **PDFs are rendered offline.** The renderer runs with JavaScript off and network requests blocked.

Not everything disappears with an account. Usage records are kept, so a free trial cannot be restarted by signing up again; they hold an internal ID, numbers and a keyed fingerprint of the email address, but no content. Backups made before the deletion still contain the data until they expire.

## A local door for your own assistant

The app includes a small MCP server that lets Claude Desktop or Claude Code read and edit the profile. It runs as a process on your own computer and talks over standard input and output, so it opens nothing to the network, and it makes no AI calls of its own. Every edit passes the same validation as an edit in the app, and every save keeps the previous profile as a version you can restore.

It works on the app's data on the same machine. It is a tool for a local installation and not part of the hosted service.

## Spending has a ceiling

All AI work runs on one provider account that I pay for, so cost control is part of the design.

- **Operations per plan.** A plan allows a fixed number of imports, tailored CVs, revisions and job searches. The limit is checked on the server before each one starts.
- **A cost cap per period.** Behind the visible limits, each account has a ceiling in dollars. A model missing from the price table is charged at the most expensive rate, so the cap errs high.
- **A ceiling per call.** Before a revision is sent, its worst case is priced. If that is too high, the call is refused and nothing is charged.
- **One AI request at a time per account.** A second parallel request is turned away. Without this, parallel requests could all pass the same limit check.
- **Limits per day.** Ten application emails per account in 24 hours, and three sign-ups per IP address per day.
- **Metered in one place.** Every AI request goes through one function that records its real token cost, so a new feature cannot skip the meter.
- **Credits pay for results.** If the AI fails, if its answer is cut off, or if a job search finds nothing new, the credit comes back.

A local simulation mode replaces the provider with fixed answers. Running out of credits can be tested without spending anything.

Note 010 said that generating a draft never adds anything to the applications list, and that only approving it does. Twenty-nine notes later I removed that approval screen, because it stood between asking for a CV and seeing it. The draft is now saved straight away, as a draft. What stayed is that sending is a separate step.

## What this does not show

The review in note 044 was a code review with local tests. It was not a penetration test, and it did not examine the live server. The measures on this page describe how the app is built. They do not certify it.

## How it is built

A Next.js application with one SQLite database per account, Claude for import, tailoring and matching, and headless Chromium for reading job pages and exporting PDFs. Accounts run on Better Auth. It is hosted on a Hetzner server with Dokploy.
